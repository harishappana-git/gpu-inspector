# Explicitly trusted OEM and driver advisory packs

This package provides the comparison source for A10 and H04. It ships no vendor key, production advisory or approved VBIOS data. Tests use signed synthetic assertions and deliberately nonexistent `example.invalid` sources; they are not vendor publications or GPU qualification evidence.

`LoadContext(ctx, path, key, now)` reads at most the existing bundle document cap, verifies the Ed25519 envelope using an explicitly supplied trusted public key, rejects unknown/duplicate JSON members, and validates the dated schema. `Load` is its background-context wrapper. `Evaluate(pack, device, retainedObservations, now)` emits exactly two observations, using method IDs `advisory.oem_vbios` and `advisory.driver_issue`. A nil pack abstains. An unsigned, changed-after-loading or expired pack produces explicit tool errors. The caller supplies only selected/retained evidence and handles load errors in its report.

The payload has `kind: "gri-advisory"`, `schema_version: "1.0.0"`, `advisory_id`, `version`, `publisher`, `issued_at`, `valid_until`, `oem`, and `driver_advisories`. Across both entry arrays the limit is 256. Every entry has a unique `id`, an exact canonical `sku`, and a `source` containing an HTTPS URL, title and publication timestamp no later than pack issuance. URLs cannot contain credentials or query parameters. The output retains the signed payload digest, trusted key fingerprint, publisher assertion, dates and matched sources. Signatures authenticate the chosen key's assertions; they do not independently prove that the signer is the claimed vendor.

An OEM entry additionally has `board_part_number` and 1–32 `vbios_versions`. A10 requires consistent retained PASS metadata for the selected UUID, from scalar fields `part_number` (or `board.part_number`) and `vbios` (or `vbios_version`). Version/part matching trims surrounding whitespace and ignores letter case only. A known tuple produces metadata-agreement PASS. An absent board, unrecognized VBIOS, missing/changed metadata or missing corpus entry remains NOT_TESTED. It never infers modified firmware, counterfeit hardware or firmware attestation.

A driver entry additionally has `driver_min`, `driver_max`, `summary`, and a `symptom` selector. Inclusive driver bounds compare 2–4 numeric components with missing trailing components treated as zero; lexical ordering and age heuristics are never used. Retained driver metadata must agree with the selected device. The selector requires an exact `check_id`, `method_id` and FAIL/WARNING `status`. Optional `field` and `value` must appear together: the value is compared with the named scalar observation field or a direct object key. Values are bounded strings, booleans or exact decimal numbers; null, arrays, nested matching, exponents and message substrings are rejected. Large integer comparisons retain exact values.

H04 matches only an explicit symptom with a retained ID, the exact selected UUID, and a valid observation timestamp. A complete SKU/range/symptom match yields WARNING as a possible documented explanation, preserving its source and evidence references. It does not establish causality, a hardware fault, a fix's applicability outside the cited conditions or a clean driver when no entry matches. Advisory results cannot match themselves as fresh symptoms.

Cancellation is checked between bounded file reads. An individual filesystem call can still block in the OS. No source URL is fetched, command executed, firmware modified, driver changed or external message sent by this package.
