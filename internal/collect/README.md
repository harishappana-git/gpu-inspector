# Read-only collection adapters

`Discover`, `GPU`, `Telemetry`, and `Host` return versioned, normalized observations. `Contracts` declares permissions, effects, cost estimates, cancellation and fallback. The production entry point must call `HandleInternalCommand` before normal CLI parsing, so management and OS reads execute in bounded child processes. Collector helpers receive only locale, a fixed executable search path, GPU visibility variables and, on Windows, OS-resolved Windows installation directories. They use the shared process runner with Unix process groups or Windows Job Objects, an output cap, and cancellation; raw stderr is classified and discarded.

On Linux builds with cgo, the NVIDIA helper loads `libnvidia-ml.so.1` at runtime. On Windows, a pure-Go adapter loads `nvml.dll` from the OS-resolved System32 or Program Files/NVIDIA Corporation/NVSMI installation location, with DLL dependencies restricted to that installation directory and System32. No CUDA toolkit/NVML headers or C compiler are required to build the Windows collector. Stable public ABI types and individually discovered symbols are used. Unavailable NVML fields can fall back to fields explicitly advertised by the installed `nvidia-smi --help-query-gpu`; selected-device values are requested in one CSV batch. Windows CLI discovery uses the same trusted installation locations, without consulting PATH, the current directory, or caller-provided SystemRoot/ProgramFiles values. NVML and nvidia-smi remain one host/driver trust domain. A cgo-free Linux build uses the CLI fallback. Other operating systems produce explicit degraded-mode observations.

The CUDA driver is loaded only for read-only enumeration of runtime-visible UUIDs (`libcuda.so.1` on Linux or System32 `nvcuda.dll` on Windows), without creating a context or allocating GPU memory. Numeric CUDA visibility masks are never interpreted as management indices. Masks are intersected with management visibility. MIG-specific masks are rejected as unsupported instead of substituting a physical parent. Full partition enumeration and vGPU qualification remain release gaps. Management visibility does not establish application usability.

GPU snapshots include identity, reported memory, supported ECC counters/state, row remapping, retired-page counts, core temperature and device-provided temperature thresholds, power, clock reasons, PCIe telemetry, utilization, and a count-only compute-process query. Windows driver-model fields report the native NVML enum (0 = WDDM, 1 = TCC, 2 = MCDM). No PIDs or process names are exported. Lightweight telemetry uses ten fields. Field statuses preserve unavailable/denied/unsupported values, and a changed UUID contaminates the snapshot. RTX 5080 MIG, ECC, retirement and remapping fields remain unsupported when the driver does not expose them; they are never fabricated as disabled or zero. WDDM desktop process counts can be nonzero even with low GPU utilization and are retained accurately. No complete Xid/event history or reliable reset epoch is claimed; a nondecreasing error counter cannot exclude an intervening reset.

Host collection reads only selected proc/sys metadata. Cgroup membership is resolved through the current process mountinfo and membership paths, including cgroup v1/v2 mount roots and readable ancestors. CPU quota and memory ceilings use the tightest readable ancestor, with hidden ancestors, incomplete reads, and sibling consumption stated as limitations. Private hierarchy paths, process identities, mount source/credentials, IP/MAC addresses, environment and raw logs are omitted. Workspace capacity and mount type are read without creating test files; statfs does not establish quota or storage persistence. Network collection reads only local IPv4 route/interface context and sends no traffic.

Windows host collection uses native read-only APIs for OS version, CPU affinity and logical-processor counts, cumulative CPU times, physical memory and process commitment context, uptime, NUMA context, filesystem capacity/type and interface counts/MTUs. Workspace paths, volume identities, interface names, IP addresses and MACs are omitted. GetSystemTimes/affinity group scope and incomplete nested Job Object limits are stated explicitly. Commit capacity is not mislabeled as pagefile size. Linux cgroups, PSI, seccomp, `/dev/shm`, and POSIX rlimits are reported unsupported on Windows; no corresponding health pass is inferred.

The Windows environment includes an OS-resolved `ProgramFiles` value. With driver 610.88, `nvidia-smi` returned `NVML: Unknown Error` when that variable was absent, even with a correct absolute executable and System32 search path. Adding only the known-folder `ProgramFiles` value resolved the failure; caller-provided installation and loader paths remain excluded. The opt-in GPU integration explicitly exercises both native NVML and the forced SMI fallback under their restricted child environments.

Validation includes malformed/absent/denied scalar parsing, observed-zero preservation, numeric CUDA remapping, partition refusal, current cgroup and ancestor-limit fixtures, traversal rejection, private-data exclusion, mismatched-UUID contamination, child cancellation, output limits and environment allowlisting. Linux mountinfo path parsing uses Linux path semantics on every test host. Collector subprocess fixtures are native Go helpers and run on Windows as well as Unix.

Windows OS collection and the public ABI structure sizes have automated tests. Set `GRI_WINDOWS_GPU_TEST=1` to run the optional installed-driver integration test, which checks bounded native discovery, CUDA UUID mapping, selected-device snapshot and telemetry. This integration passed on the local Windows RTX 5080 with driver 610.88 on 2026-09-07. This establishes observed collector functionality on that configuration, not GPU performance, health, or qualification for other hardware/drivers. Linux cgo-free cross-compilation remains a development check; H100 Linux hardware qualification is separate.
